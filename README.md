# D20DAO Randomizer Demo

Live on Arc Mainnet: **https://mainnet-demo.d20dao.org**

A small dapp that requests every randomness option in [`@d20dao/vrf-sdk`](https://github.com/d20dao/d20-sdk) 0.4.0 from the published D20DAO coordinator on Arc Mainnet (chain 5042) or Arc Testnet (chain 5042002). The contract stores the latest fulfilled result for each option and the last 20 fulfilled results. The page reads that stored state every few seconds, so it shows new results from any wallet as they arrive.

Requests on mainnet spend real USDC: the D20DAO fee (0.08 USDC minimum) plus gas. Check requests on the [D20DAO Explorer](https://arc.d20dao.org).

This is example code, not audited, and has no application payments, eligibility rules or access control beyond the randomness fee.

- `contracts/D20Playground.sol`: the consumer contract. It extends `D20VRFConsumer`, has one payable function per option, and exposes read functions for the stored results.
- `frontend/index.html`: a single-page UI. It has a network selector, a live view of stored results, a wallet request flow, and refund and retry actions.
- `frontend/networks.json`: public network and coordinator settings, generated by `npm run build`.
- `frontend/deployments.json`: the contract address for each chain id, written by the deploy script.
- `scripts/`: compile, pre-flight check, keyless live dry run, deploy and serve.
- `test/`: a local end-to-end test with a mock coordinator.
- `wrangler.jsonc` and `worker/index.js`: static hosting of `frontend/` on a Cloudflare Worker, plus a read-only RPC relay.

## Options covered

| Kind | Card | Contract function | SDK call inside the contract | Result |
| --- | --- | --- | --- | --- |
| 0 | Raw word | `requestRaw(context)` | `rng.requestRandomness{value: fee}` | one 256-bit word |
| 1-6 | d20, d12, d10, d8, d6, d4 | `rollD20(context)` ... `rollD4(context)` | `rng.d20(o)` ... `rng.d4(o)` | one value 1..sides |
| 7 | Custom die | `rollDN(sides, context)` | `rng.dN(sides, o)` | one value 1..sides |
| 8 | Dice roll | `rollDice(sides, count, context)` | `rng.diceRoll(sides, count, o)` | `count` values |
| 9 | Coin flip | `flipCoin(context)` | `rng.coinFlip(o)` | 0 = tails, 1 = heads |
| 10 | Number range | `randomInRange(min, max, context)` | `rng.numberRange(min, max, o)` | one value in [min, max] |
| 11 | Choose one | `chooseOne(string[] items)` | `rng.chooseOne(n, o)` | one index into `items` |
| 12 | Choose many | `chooseMany(string[] items, count)` | `rng.chooseMany(n, count, o)` | distinct indices |
| 13 | Shuffle | `shuffle(string[] items)` | `rng.shuffle(n, o)` | permutation of indices |

For choose one, choose many and shuffle, the contract hashes the ordered list on-chain (`keccak256(abi.encode(items))`) before the request and binds the hash into the client seed. It also emits the list in `ItemsCommitted`, so any viewer can map the indices back to the committed items.

## Stored results and read functions

| Function | Returns |
| --- | --- |
| `latestResults()` | `Result[14]`, indexed by kind: the most recent fulfilled result for every option (`requestId` 0 means none yet) |
| `latestResult(kind)` | the same record for one option |
| `recentResults()` | up to `HISTORY_SIZE` (20) most recent fulfilled results across all options, newest first |
| `getResult(requestId)` | the record for any request through this contract, including pending and refunded ones |
| `jobIdsOf(address)`, `requestCount()`, `fulfilledCount()` | per-wallet request ids and counters |

`Result` contains `requestId`, `requester`, `kind`, `status` (1 pending, 2 fulfilled, 3 refunded), `requestedAt`, `requestBlock`, `fulfilledAt`, `fulfilledBlock`, `context` (a label, or the items hash), `word` (the raw word delivered by the coordinator), `spec` (the mapping the coordinator stored for the request) and `mappedValues`.

**How mapped values are stored.** The callback runs on the fixed `CALLBACK_GAS` budget, 150,000 gas. Storing mapped values directly would scale with result size: a 256-item shuffle needs about 5.6M gas, far above the coordinator's `MAX_CALLBACK_GAS` of 1,000,000. So the callback writes a fixed-size record: the word, the fulfillment block and time, and pointers in the per-option and history lists. The request transaction copies the mapping spec from `coordinator.getMapping(id)`. The read functions compute `mappedValues` with the SDK's `RandomnessMapping.map(word, spec)`, the same library and inputs the coordinator's `getMappedResult` uses. The values are therefore fully determined by this contract's storage and do not need the coordinator at read time.

Measured callback gas is about 103k in the worst case, the first result ever when every slot is fresh (live `eth_estimateGas` on both networks; about 105k in the local test). Steady state is about 51k.

## Payment

The page quotes the fee with the SDK's `quoteRequestFee(provider, coordinator, CALLBACK_GAS, { bufferBps: 3000 })` and sends the result as `msg.value`. The contract pays the exact in-transaction `quoteFee(CALLBACK_GAS)` through the `D20VRFRequests` helper and returns the change. The requester is the fixed refund address.

At a 20 gwei base fee, both networks currently charge the 0.08 USDC minimum per request. Each request also pays its own gas. Deployment uses about 2.34M gas.

## Setup

Node 22.13 or newer.

```sh
npm install
npm run build            # compile (solc 0.8.28), bundle ethers + SDK for the browser, write frontend/networks.json
npm run check:service    # read-only, both networks: chain id, coordinator implementation and code hash vs pins and live manifest, pricing
npm run simulate         # keyless dry run against the live coordinators on both networks (eth_call with state overrides)
npm run test:local       # full local end-to-end test on local chains with the testnet and mainnet chain ids
```

## Deploy

The key is read only from the `PRIVATE_KEY` environment variable and is never written to disk. The script:
1. runs the pre-flight check;
2. refuses to deploy if the coordinator no longer matches the published manifest (override with `ALLOW_UNPINNED_COORDINATOR=1`);
3. checks the balance against the estimated cost;
4. deploys and verifies that the contract points at the published coordinator;
5. records the address under the chain id in `frontend/deployments.json`.

Arc Testnet (test USDC from https://faucet.circle.com):

```powershell
$env:PRIVATE_KEY = "0x..."
npm run deploy:testnet
Remove-Item Env:PRIVATE_KEY
```

Arc Mainnet (real USDC). Without the flag, the script only runs the pre-flight and cost estimate, then exits:

```powershell
$env:PRIVATE_KEY = "0x..."
npm run deploy:mainnet                        # pre-flight + cost estimate only, sends nothing
npm run deploy:mainnet -- --confirm-mainnet   # deploys
Remove-Item Env:PRIVATE_KEY
```

With bash, use `PRIVATE_KEY=0x... npm run deploy:mainnet -- --confirm-mainnet`. RPC overrides are `ARC_TESTNET_RPC_URL` and `ARC_MAINNET_RPC_URL`. The defaults are Arc's public `https://rpc.testnet.arc.io` and `https://rpc.mainnet.arc.io`.

## Host the page

`npm run deploy:worker` builds the project and uploads `frontend/` as static assets to a Cloudflare Worker (free plan). Arc's public RPC endpoints are on `*.arc.io`, which common ad-block lists block in browsers (`net::ERR_BLOCKED_BY_CLIENT`). The page therefore checks the public RPC first and otherwise reads through `/rpc/<chainId>`, a relay in `worker/index.js` that forwards only read methods; wallets still send transactions through their own RPC. Static files never invoke the Worker, and relayed pages poll every 8 seconds and pause in background tabs. `npm run serve` provides the same relay locally. `wrangler.jsonc` binds it to `mainnet-demo.d20dao.org`; change `name` and `routes` for your own domain, and run `npx wrangler login` first. If your login has more than one Cloudflare account, set `CLOUDFLARE_ACCOUNT_ID`. On a host name starting with `mainnet`, the page opens on Arc Mainnet.

## Open the page locally

```sh
npm run serve
```

- Testnet: http://localhost:5173/?network=testnet
- Mainnet: http://localhost:5173/?network=mainnet

The network selector reloads the page for the other network, and the choice is remembered. The page reads the contract address for the selected chain from `frontend/deployments.json` and refreshes stored results every 4 seconds, with or without a wallet. On mainnet it shows a "real USDC" badge and asks for confirmation before sending.

Optional URL parameters:
- `consumer=0x...` overrides the contract address.
- `rpc=https://...` overrides the RPC for the selected network.
- `deployments=file.json` loads a different config file from `frontend/`.
- `poll=ms` changes the refresh interval.

## Local test details

`npm run test:local` does the following:
1. Starts two Hardhat nodes with chain ids 5042002 and 5042.
2. Puts `test/MockCoordinator.sol` at each network's published coordinator proxy address, and the real implementation code (fetched read-only) at the pinned implementation address, so the deploy pre-flight's code-hash check runs for real.
3. Deploys with `scripts/deploy.mjs`. On mainnet it first checks that deploying without `--confirm-mainnet` sends nothing.
4. Requests every option from wallet A and checks the exact fee and returned change, the stored spec against `getMapping`, and the committed item list.
5. Fulfills every request and checks the stored word and block, and that `mappedValues` equals both the SDK's `mapRandomness` and `getMappedResult`.
6. Checks `latestResults()` and `recentResults()`.
7. Has wallet B replace some latest results.
8. Wraps the 20-entry history.
9. Tests callback failure followed by `retryCallback`, expiry followed by a refund by another wallet, and the auth, underpayment and invalid-mapping rejections.

`npm run test:local:keep` leaves both chains and the page server running and prints page URLs. While it runs:
- `node test/local-e2e.mjs request --network testnet --options d20,shuffle` makes requests from another wallet.
- `node test/local-e2e.mjs keeper --network testnet` fulfills pending requests.
